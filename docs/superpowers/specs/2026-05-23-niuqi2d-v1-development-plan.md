# NiuQI2D v1 开发计划

## 1. 计划目标

本开发计划基于 `TASK_BREAKDOWN.md` 与 `docs/superpowers/specs/2026-05-23-niuqi2d-v1-design.md` 制定，目标是把 NiuQI2D v1 从产品设计拆解为可执行的开发阶段、Agent 分工、串并行关系和交付验收标准。

v1 的核心目标不是一次性覆盖所有 2D 游戏素材类型，而是先跑通一个可靠闭环：

用户输入文本和简单参数 -> Prompt 优化 -> 图像 API 生成 -> 本地图像后处理 -> 入库管理 -> PNG / Sprite Sheet / JSON 导出 -> 能被 Unity、Godot、Cocos 等主流 2D 工具链使用。

## 2. 开发阶段拆分

建议拆分为 6 个阶段。前 2 个阶段建立基础工程与核心技术可行性，第 3-4 个阶段完成产品闭环，第 5 阶段提升项目化和风格一致性，第 6 阶段做打磨、测试和发布。

### 阶段 0：项目基线与技术 Spike

目标：确认关键技术路线可跑通，避免后续大规模开发后发现核心生成或后处理不可用。

主要任务：

- 确认桌面应用技术栈：Electron + React + TypeScript。
- 确认本地服务技术栈：Python + FastAPI。
- 确认本地存储方案：SQLite + 文件系统。
- 验证 Electron 主进程能拉起 Python FastAPI 子进程。
- 验证前端能通过 localhost HTTP 调用 Python 服务。
- 验证至少一个图像生成 API 可用。
- 验证 Prompt 优化 API 可用。
- 验证一张生成图片能完成透明化、裁切、尺寸标准化、像素化、色板量化。

阶段交付物：

- 最小工程骨架。
- Python 服务健康检查接口。
- 前端调用后端的最小 Demo。
- 图像生成和后处理 Spike 报告。

串行依赖：

- 必须先完成技术 Spike，才能进入完整生成闭环开发。
- API Key 配置和后处理算法验证是阶段 1 的前置条件。

可并行任务：

- Electron 工程骨架、FastAPI 服务骨架、图像后处理 Spike 可以并行。
- Prompt 模板研究和导出 JSON 格式细化可以并行。

### 阶段 1：基础框架与数据底座

目标：建立可持续开发的桌面应用框架、后端服务框架和核心数据模型。

主要任务：

- 搭建 Electron 主进程、渲染进程、窗口管理和 Python 子进程管理。
- 搭建 React + TypeScript 前端基础布局。
- 建立左侧项目栏 + 主内容区的桌面工具型布局。
- 搭建 FastAPI 服务，定义统一响应结构和错误结构。
- 建立 SQLite 数据表：Project、StyleProfile、Asset、GenerationRecord、ExportRecord。
- 建立文件存储目录规范：原图、处理图、缩略图、导出包、参考图。
- 实现项目创建、项目切换、默认项目初始化。
- 实现 API Key 设置的本地保存方案。

阶段交付物：

- 应用可启动。
- Python 服务随应用启动和关闭。
- 前端可以读写项目和基础设置。
- 数据库可初始化、迁移和查询。

串行依赖：

- 数据模型和存储目录规范应先定稿，资产库、生成记录和导出功能才能稳定开发。
- Python 服务生命周期需要先完成，后续生成、后处理、导出 API 才能接入。

可并行任务：

- 前端基础布局可与 SQLite 数据模型开发并行。
- 设置页 API Key 表单可与项目管理接口并行。

### 阶段 2：生成闭环 MVP

目标：让用户能从文本输入生成素材，并得到可预览、可保存的结果。

主要任务：

- 实现生成页 UI：素材类型、文本描述、参数表单、参考图上传、快速预览、高质量生成按钮。
- 实现素材类型模板：角色动画、地图 Tile。
- 实现 Prompt Optimizer：将用户描述、素材类型、风格参数重写为图像生成 Prompt。
- 实现图像生成 Engine：调用商业图像 API，支持候选图数量和生成模式。
- 实现异步生成任务：等待、生成中、后处理中、完成、失败。
- 实现候选结果网格预览，支持透明棋盘格背景。
- 实现选择候选并加入资产库。
- 保存 GenerationRecord 和 Asset。

阶段交付物：

- 用户可以输入描述并生成候选图。
- 候选图可预览、选择、入库。
- 每次生成保留原始 Prompt、优化 Prompt、模型参数、成本估算和后处理记录。

串行依赖：

- Prompt Optimizer 输出结构必须先确定，图像生成 Engine 才能稳定调用。
- 生成任务状态协议必须先确定，前端进度展示和后端队列才能对齐。

可并行任务：

- 生成页 UI 可与后端生成任务 API 并行。
- Prompt 模板可与图像 API Provider 封装并行。
- 候选图预览可先使用 mock 数据开发。

### 阶段 3：图像后处理与导出闭环

目标：把 AI 输出变成游戏开发可直接使用的工程资产。

主要任务：

- 实现后处理管线：去背景、裁切、居中、尺寸标准化。
- 实现像素风处理：最近邻缩放、K-Means 色板量化、抗锯齿和脏边检查。
- 实现缩略图生成。
- 实现 Sprite Sheet 拼接。
- 实现帧 JSON 元数据生成。
- 实现 Tileset JSON 元数据生成。
- 实现导出页 UI：资产选择、导出类型、导出配置、导出路径、导出进度。
- 实现导出历史记录。
- 完成 Unity/Godot 通用导入验证。

阶段交付物：

- 单图 PNG 导出。
- Sprite Sheet PNG + JSON 导出。
- Tileset PNG + JSON 导出。
- 导出结果可被主流 2D 引擎导入。

串行依赖：

- 后处理输出规范必须先稳定，Sprite Sheet 和 JSON 导出才能稳定。
- Asset 数据结构必须先可用，导出页才能做批量选择和记录。

可并行任务：

- 后处理算法可与导出页 UI 并行。
- Sprite Sheet 拼接可与 Tileset JSON 格式实现并行。
- 引擎导入验证可在第一版导出文件生成后独立进行。

### 阶段 4：资产库、风格与项目管理增强

目标：让工具从“单次生成器”升级为“项目级素材生产工具”。

主要任务：

- 实现资产库页面：列表、网格、筛选、搜索、状态、标签。
- 实现资产详情面板：大图预览、动画播放、生成参数、复现、变体。
- 实现风格档案 CRUD。
- 实现内置 3-5 个风格预设。
- 实现参考图上传与风格档案绑定。
- 实现项目默认风格绑定。
- 实现生成时临时覆盖风格参数。
- 实现同项目风格一致性基础检查：尺寸、色板、透明背景、透视参数。

阶段交付物：

- 用户能围绕项目管理资产。
- 用户能复用同一风格档案持续生成素材。
- 用户能对已有资产进行复现和变体生成。

串行依赖：

- 基础生成闭环和 Asset 入库必须先完成，资产库增强才有真实数据。
- 风格档案模型需要先稳定，Prompt Optimizer 才能接入风格约束。

可并行任务：

- 资产库 UI 可与风格 CRUD API 并行。
- 内置风格预设可与参考图上传功能并行。
- 复现和变体生成可在 Prompt Optimizer 稳定后独立开发。

### 阶段 5：产品化、测试与发布

目标：把 Demo 级工具打磨成可安装、可使用、可排错的 v1 产品。

主要任务：

- 完成设置页：API Provider、API Key、默认参数、存储目录、缓存清理。
- 完成连接测试和错误提示。
- 完成成本统计：调用次数、估算费用、失败次数。
- 完成快捷键和常用交互打磨。
- 完成异常处理：API 失败、网络失败、后处理失败、导出失败、磁盘权限失败。
- 完成日志系统：前端日志、后端日志、任务日志。
- 完成端到端测试：生成、入库、导出、复现。
- 完成 Windows 安装包打包。
- 编写 README、使用说明、API Key 配置说明和已知限制。

阶段交付物：

- Windows 可安装包。
- 完整 v1 使用说明。
- 端到端测试报告。
- 已知问题清单。

串行依赖：

- 核心生成、入库、导出闭环完成后才能进入完整产品化测试。
- 打包发布必须在 Python 子进程、文件存储、API Key 保存都稳定后进行。

可并行任务：

- 文档编写可与测试修复并行。
- 错误文案、空状态和快捷键打磨可与打包配置并行。

## 3. Agent 配置建议

建议使用 6 个开发 Agent 加 1 个产品统筹 Agent，共 7 个角色。

其中产品统筹 Agent 不直接长期写代码，负责拆需求、验收、协调依赖、维护范围边界。其余 6 个 Agent 按工程边界拆分，尽量减少文件冲突。

### Agent 0：产品经理 / 项目统筹

职责：

- 维护 v1 范围，防止需求膨胀。
- 将设计文档转化为阶段任务和验收标准。
- 协调 Agent 之间的依赖和交付顺序。
- 维护开发看板、里程碑和风险清单。
- 对每个阶段做产品验收。

建议提示词：

```text
你是 NiuQI2D v1 的产品经理和项目统筹。请基于仓库中的 TASK_BREAKDOWN.md、v1 design 和 development plan 管理需求范围。你的目标是确保 v1 跑通“文本生成 2D 游戏素材 -> 后处理 -> 入库 -> PNG/Sprite Sheet/JSON 导出”的闭环。

工作原则：
1. 优先保证 MVP 闭环，不主动扩大范围。
2. 每个需求都要落到用户场景、验收标准和工程模块。
3. 发现跨 Agent 依赖时，先明确接口、数据结构和完成定义。
4. 每个阶段结束时输出验收清单、遗留问题和下一阶段建议。
5. 对高风险项保持敏感：生成质量、成本、风格一致性、导出兼容性。

请不要直接重构工程代码，除非任务明确要求你修正文档、计划或验收标准。
```

### Agent 1：桌面端架构 / Electron 主进程

职责：

- 搭建 Electron 应用。
- 管理窗口、应用菜单、文件选择、系统路径。
- 拉起、监控和关闭 Python FastAPI 子进程。
- 管理主进程与渲染进程安全边界。
- 处理打包时的 Python 服务路径和资源路径。

建议提示词：

```text
你是 NiuQI2D v1 的桌面端架构工程师，负责 Electron 主进程和桌面应用生命周期。你不负责 React 页面业务实现，也不负责 Python 业务逻辑。

你的工作范围：
1. Electron 应用启动、窗口管理、开发/生产环境路径处理。
2. Python FastAPI 子进程启动、健康检查、端口发现、关闭和异常重启。
3. 为渲染进程暴露安全的 preload API，例如选择导出目录、读取应用版本、获取后端服务地址。
4. 打包发布所需的桌面端配置。

协作要求：
- 与后端 Agent 约定 /health 接口和服务启动参数。
- 与前端 Agent 约定 preload API 名称和返回结构。
- 不要修改后端业务接口，除非接口契约已经更新。
- 不要覆盖其他 Agent 的前端页面或 Python 业务代码。
```

### Agent 2：前端产品体验 / React UI

职责：

- 实现 React + TypeScript 渲染进程。
- 实现生成页、资产库、导出页、设置页。
- 实现桌面工具型布局、状态反馈、空状态、错误提示。
- 实现透明棋盘格图片预览和动画播放预览。
- 对接后端 HTTP API 和 Electron preload API。

建议提示词：

```text
你是 NiuQI2D v1 的前端产品体验工程师，负责 React + TypeScript UI。请按照 v1 design 中的桌面工具型产品要求实现页面，不做营销页，不做移动端适配，优先保证 1024px 以上桌面体验。

你的工作范围：
1. 左侧项目栏 + 主内容区布局。
2. 生成页：素材类型、文本输入、动态参数、参考图上传、快速预览/高质量生成、候选结果网格。
3. 资产库：筛选、搜索、网格/列表、详情面板、批量选择。
4. 导出页：资产选择、导出类型、参数表单、路径选择、进度、历史。
5. 设置页：API 配置、默认参数、存储管理。

体验要求：
- 所有图片预览默认使用棋盘格透明背景。
- 异步任务必须有明确状态反馈。
- 表单和按钮文案应面向游戏开发者，清晰、克制、专业。
- 优先对接真实 API；接口未完成时使用 mock 但保留替换点。

协作要求：
- 与后端 Agent 对齐 API 类型定义。
- 不要修改 Electron 主进程生命周期代码。
- 不要修改 Python 后处理算法代码。
```

### Agent 3：后端 API / 任务队列 / 数据库

职责：

- 实现 FastAPI 服务。
- 实现 SQLite 数据模型和迁移。
- 实现项目、风格、资产、生成记录、导出记录 API。
- 实现异步任务状态管理。
- 统一错误、日志和响应格式。

建议提示词：

```text
你是 NiuQI2D v1 的后端应用工程师，负责 Python FastAPI、SQLite、任务状态和业务 API。你不负责图像生成模型调用细节，也不负责图像处理算法实现，但需要为它们提供清晰接口。

你的工作范围：
1. FastAPI 应用结构、/health、统一响应和错误格式。
2. SQLite 数据模型：Project、StyleProfile、Asset、GenerationRecord、ExportRecord。
3. 文件存储路径规范：source、processed、thumbnail、exports、references。
4. 业务 API：项目管理、风格管理、资产管理、生成任务、导出记录。
5. 异步任务状态：pending、generating、postprocessing、completed、failed。

协作要求：
- 与 Electron Agent 对齐服务启动和健康检查。
- 与前端 Agent 对齐 API schema。
- 与 AI Agent 对齐生成任务输入输出。
- 与图像处理 Agent 对齐后处理函数接口。
- 不要在业务 API 中硬编码具体模型 Provider。
```

### Agent 4：AI 生成 / Prompt Optimizer

职责：

- 实现 Prompt 优化模块。
- 封装文本 LLM 调用。
- 封装图像生成 Provider。
- 管理素材类型 Prompt 模板。
- 支持快速预览和高质量生成两档。
- 记录 API 参数、成本估算、失败原因。

建议提示词：

```text
你是 NiuQI2D v1 的 AI 生成工程师，负责 Prompt Optimizer 和图像生成 Engine。你的目标不是追求最复杂模型能力，而是为 v1 提供稳定、可控、低成本的生成入口。

你的工作范围：
1. 将用户原始描述、素材类型、风格档案、参数表单重写为图像生成 Prompt。
2. 为角色动画和 Tile 两类素材维护 Prompt 模板。
3. 封装图像生成 API Provider，至少支持一个可配置 Provider。
4. 支持快速预览和高质量生成两种模式。
5. 返回原始图片路径、优化 Prompt、模型参数、成本估算和错误信息。

质量要求：
- Prompt 输出要强调 2D game asset、transparent background、consistent style、clear silhouette、fixed perspective 等游戏素材约束。
- 像素风素材要强调 clean edges、limited palette、no blur、no antialiasing，但最终质量仍交给后处理管线兜底。
- 所有 API Key 必须从设置或环境配置读取，不能写死。

协作要求：
- 与后端 Agent 对齐生成任务输入输出结构。
- 与图像处理 Agent 对齐原始图交付格式。
- 不要直接写前端页面。
```

### Agent 5：图像后处理 / 导出算法

职责：

- 实现本地图像后处理。
- 实现透明背景、裁切、居中、缩放、色板量化。
- 实现 Sprite Sheet 和 Tileset 拼接。
- 实现 JSON 元数据生成。
- 实现质量检查报告。

建议提示词：

```text
你是 NiuQI2D v1 的图像后处理与导出算法工程师，负责把 AI 生成图变成游戏引擎可用资产。你的重点是确定性、可复现、工程兼容，而不是再次调用生成模型。

你的工作范围：
1. 透明背景处理，优先处理已有 alpha，必要时接入 rembg 或替代方案。
2. 自动裁切、补边、居中、锚点标准化。
3. 像素风最近邻缩放，避免模糊和抗锯齿。
4. K-Means 或调色板量化，支持 16/32 色等限制。
5. Sprite Sheet 拼接和 frame JSON 元数据生成。
6. Tileset PNG + JSON 元数据生成。
7. 输出后处理日志和质量检查结果。

协作要求：
- 与后端 Agent 对齐函数输入输出和文件路径。
- 与前端 Agent 对齐预览所需缩略图和动画帧信息。
- 与 AI Agent 对齐原始图片输入格式。
- 不要修改图像生成 API 调用逻辑。
```

### Agent 6：测试 / 兼容性 / 发布

职责：

- 设计和执行端到端测试。
- 验证 Unity/Godot/Cocos 通用导入。
- 验证 Windows 打包。
- 验证错误处理、日志、成本统计。
- 编写用户文档和已知限制。

建议提示词：

```text
你是 NiuQI2D v1 的测试、兼容性和发布工程师。你的目标是确保 v1 能作为一个 Windows 桌面工具被安装、启动、生成素材、导出文件，并被主流 2D 游戏开发工具使用。

你的工作范围：
1. 编写端到端测试清单：生成、入库、导出、复现、异常处理。
2. 验证导出文件：PNG、Sprite Sheet + JSON、Tileset + JSON。
3. 验证 Unity/Godot/Cocos 的通用导入可行性，记录步骤和问题。
4. 验证 Windows 打包、安装、启动和卸载。
5. 检查 API Key 缺失、网络失败、生成失败、导出路径无权限等异常场景。
6. 编写 README、使用说明、配置说明和已知限制。

协作要求：
- 不要大规模改动产品代码；发现问题先提交可复现报告。
- 小型修复可以直接提交，但必须说明影响范围。
- 测试结论必须包含环境、步骤、期望结果、实际结果。
```

## 4. 推荐 Agent 数量与投入方式

推荐配置：7 个 Agent。

- 1 个产品统筹 Agent。
- 1 个 Electron 桌面端 Agent。
- 1 个 React 前端 Agent。
- 1 个 FastAPI 后端 Agent。
- 1 个 AI 生成 Agent。
- 1 个图像后处理与导出 Agent。
- 1 个测试与发布 Agent。

如果资源有限，可以压缩为 4 个 Agent：

- 产品统筹 + 测试发布合并。
- Electron + React 前端合并。
- FastAPI + SQLite + 任务队列合并。
- AI 生成 + 图像后处理 + 导出合并。

如果追求更快并行，可以扩展为 9 个 Agent：

- 将前端拆为生成页 Agent、资产库/导出页 Agent。
- 将图像后处理和导出格式拆成两个 Agent。
- 将测试和文档拆成两个 Agent。

v1 推荐不要超过 7 个长期 Agent。超过 7 个后，接口协调成本会明显上升。

## 5. 串行开发关系

以下任务建议严格串行或半串行推进。

### 5.1 必须先做的任务

1. 技术 Spike。
2. 工程骨架。
3. 后端 API 契约。

## 8. 接口优先级

为了减少并行开发冲突，建议优先确定以下接口。

### 8.1 核心枚举

- AssetType：character、tile、prop、ui、effect。v1 先启用 character、tile。
- JobStatus：pending、generating、postprocessing、completed、failed。
- ExportFormat：png_single、spritesheet_png_json、tileset_png_json。
- AssetStatus：draft、selected、exported、discarded。

### 8.2 核心请求

- CreateGenerationJobRequest。
- OptimizePromptRequest。
- PostprocessImageRequest。
- CreateAssetRequest。
- ExportAssetsRequest。

### 8.3 核心输出

- GenerationJob。
- CandidateImage。
- ProcessedAsset。
- AssetDetail。
- ExportRecord。
- StyleProfile。

这些类型建议放在共享 schema 文件或 OpenAPI 生成流程中，避免前后端字段漂移。

## 9. 第一轮开发的推荐顺序

第一轮不要试图做完整产品，建议只做一条最短闭环。

1. 创建默认项目。
2. 配置 API Key。
3. 在生成页输入一句话。
4. Prompt Optimizer 返回优化 Prompt。
5. 图像 API 返回 1-2 张候选图。
6. 后处理生成透明 PNG。
7. 候选图显示在棋盘格预览中。
8. 用户选择一张加入资产库。
9. 用户导出单图 PNG。
10. 记录 GenerationRecord 和 ExportRecord。

完成这条闭环后，再扩展 Sprite Sheet、Tileset、风格档案和资产库高级管理。

## 10. v1 验收标准

### 10.1 产品验收

- 用户首次打开应用后，可以完成 API Key 配置。
- 用户可以创建或使用默认项目。
- 用户可以通过文本生成 2D 游戏素材候选图。
- 用户可以将候选图加入资产库。
- 用户可以导出 PNG、Sprite Sheet + JSON、Tileset + JSON。
- 导出文件结构对游戏开发者可理解，不需要额外查内部实现。

### 10.2 技术验收

- Electron 能稳定拉起和关闭 Python 服务。
- 后端任务状态能被前端实时或准实时查询。
- SQLite 能保存项目、风格、资产、生成记录、导出记录。
- 图像后处理流程可重复执行，不破坏透明通道。
- 导出 JSON 符合设计文档中的 schema。
- Windows 安装包可安装和启动。

### 10.3 质量验收

- 从输入文本到获得可用 PNG，正常网络下控制在 1 分钟左右。
- 生成失败时用户能看到明确错误，而不是静默失败。
- 同一项目同一风格下的素材在尺寸、色板和透视上基本一致。
- Sprite Sheet 帧尺寸一致，动画预览无明显跳动。
- Tile 导出至少满足基础网格尺寸和 JSON 元数据正确。

## 11. 主要风险与决策点

### 11.1 图像 API 选择

决策点：优先使用 OpenAI 图像 API 还是 Stable Diffusion 类第三方 API。

建议：v1 支持 Provider 抽象，先接一个最稳定的 Provider，不要在 v1 同时深度适配多个模型平台。

### 11.2 像素风质量

风险：图像模型输出可能不像真正像素素材。

建议：v1 不依赖模型一次生成完美像素图，而是用后处理兜底：最近邻缩放、色板量化、裁切、透明化。

### 11.3 动画一致性

风险：角色多帧动画容易发生形变和抖动。

建议：v1 可先支持简单 Sprite Sheet 拼接和帧对齐，不承诺复杂四方向动作生成的高稳定性。

### 11.4 导出兼容

风险：不同引擎对元数据格式要求不同。

建议：v1 只承诺通用 PNG + JSON，后续再做 Unity/Godot/Cocos 原生适配器。

### 11.5 成本控制

风险：用户反复生成导致 API 成本不可控。

建议：提供快速预览、高质量生成两档；记录调用次数和估算成本；失败任务不要重复扣算。
